Qué le falta al port, medido

El código del juego no se decompila: los 11,2 MB de ARM64 de main corren tal cual en la Flip. Lo que hay que portar es todo lo que ese código pide de fuera: las funciones del SDK de Nintendo y la API gráfica NVN. Este mapa cruza cada cosa que el juego importa con lo que hace hoy nuestra implementación.

Cómo se sabe qué falta

  1. Estático, antes de ejecutar. La tabla de imports del ejecutable dice qué funciones pide; el desensamblado dice desde cuántos sitios las llama. Para NVN, cada nombre que el juego pasa a nvnDeviceGetProcAddress se sigue hasta su ranura y se cuentan las lecturas. Así salen este mapa y la lista de stubs.
  2. En ejecución. El cargador cuenta cada llamada a un stub y el ejecutor avisa de lo que no soporta (por ejemplo, transform feedback). Eso dice qué se usa de verdad en cada escena.
  3. Por comportamiento. Lo que más cuesta no son funciones que faltan, sino funciones implementadas que hacen algo distinto que en la Switch. Hoy fueron tres: los mips a cero de las texturas (ropa negra, iconos y ventanas invisibles), los draws con el rasterizador descartado (personajes sin skinning) y la caché que no avisaba de escrituras de la CPU (película congelada). Ningún mapa estático los ve: salen de comparar trazas del frame con la referencia.

Un mapa de decompilación como el de Pokémon HeartGold mide otra cosa: cuánto código del juego se ha reescrito en C idéntico al original. Aquí ese código no se toca; el equivalente es cuánta interfaz está implementada y, sobre todo, cuánta se comporta igual.
